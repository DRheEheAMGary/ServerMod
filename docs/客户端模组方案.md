# 客户端模组（双端）方案 · 成本评估

> 状态：**选型已定，尚未开工**（实现排在[钓竿系统](钓竿系统方案.md)之前：客户端渲染与界面先做）。
> 本文记录选型、目标架构、工作量分解、代价与风险，以及和现有服务端代码的衔接方式。

## 1. 已定选型

| 决策 | 选择 | 影响 |
|---|---|---|
| 模组形态 | **两个独立模组**（`hubsuite` + `hubsuite-client`） | 两份产物、版本必须同步；好处是客户端模组可独立迭代 |
| 兼容策略 | **强制安装** | 玩家门槛最高；服务端需要自己实现"没装就拦"的握手 |
| 客户端负责范围 | **直接替代全部**（渲染 + 界面 + 动态表现 + 取代 Polymer） | 现有物品注册方式要迁移成"真物品" |
| 部件外观 | **运行时逐层渲染**（匠魂式） | 任意组合、任意花纹、升级叠加层，不再需要预生成组合模型 |
| Polymer | **逐步换成真物品** | 过渡期两套并存，最终移除 Polymer 依赖 |
| 资源包 | **去掉**，素材内置进客户端模组 | 不再下发资源包；原版客户端看不到外观（与强制安装配套） |
| 测试 | 我做 `runClient` 开发客户端自测 + 你装 jar 实机验收 | 客户端渲染/界面无法被服务端自检覆盖 |
| 开工顺序 | **先做客户端渲染与界面** | 但必须先有最小"数据契约"（见第 5 节） |
| 版本绑定 | **严格同版本**（客户端必须与服务端完全一致） | 靠根目录共享的 `mod_version` + 客户端 `fabric.mod.json` 的 `depends` 保证 |

## 2. 目标架构

`~
仓库（同一仓库，多项目 Gradle）
├─ 根项目 = hubsuite（现有服务端模组，位置不变）
│   └─ gradle.properties: mod_version —— 两个模组共用，保证严格同版本
├─ client/ = hubsuite-client（新，Fabric 客户端模组）
│   ├─ 注册与自己服务端完全一致的物品 id（真物品，客户端直接认识）
│   ├─ 运行时分层物品渲染器（杆 / 线 / 钩 / 升级层）
│   ├─ 装配台的自定义 Menu + Screen（不再借原版壳）
│   └─ 内置全部素材（物品贴图 / GUI 底图）—— 不需要资源包
`~

- **版本同步**：`gradle.properties` 里一个 `mod_version`，两个模组都读它；客户端 `fabric.mod.json` 写 `depends: { hubsuite: "=<version>" }`；服务端**不**依赖客户端模组；
- **强制安装怎么落地**：Fabric 不会自动校验客户端装没装 → 需要在服务端自己实现**握手**（登录后发自定义 payload，若干秒内收不到客户端应答就断开/提示），约 50 行；
- **玩法权威性**：客户端模组**只做表现层**（渲染 / 界面 / 动效），所有判定（属性、消耗、断线、附魔）仍在服务端 —— 双端不等于把逻辑搬到客户端。

## 3. 代价与风险（选型的直接后果）

1. **每次服务端更新，所有玩家必须同步更新客户端模组**，否则进不去 —— 这是"强制安装 + 严格同版本"的必然代价，也是长期运维的主要成本；
2. **去掉 Polymer 后没有兜底**：客户端不装或版本不符时看到的是未知物品/缺失模型（这正是"强制"的含义）；迁移期间靠"Polymer 与真物品并存"过渡；
3. **物品注册方式迁移**：现在所有自定义物品都靠 Polymer 映射成原版物品；改成真物品要逐个过一遍（地狱线、三种渔桶、以及钓竿系统的部件），并重做物品显示；
4. **资源包下线**：素材要从"服务端 jar + Polymer 下发"改成"客户端模组内置"，仓库里要重新组织素材位置（现有 `src/main/resources/assets/hubsuite/**` 会拆成服务端/客户端两份或共用）；
5. **测试缺口**：服务端自检（现有 235 项）覆盖不到客户端渲染与界面 → 每轮都要实机看（你那边验收 + 我这边 `runClient`）；
6. **分发**：严格同版本意味着要有一个可靠的"哪里下载/怎么更新"的渠道（未定，见第 7 节）。

## 4. 工作量分解

| 工作项 | 估算 |
|---|---|
| 多项目 Gradle 改造（根保持服务端 + `client/` 子项目 + 共享版本） | 0.5~1 天 |
| 客户端模组骨架（entrypoint、物品注册同步、开发用 `runClient`） | 0.5 天 |
| 最小数据契约（钓竿组件 + 部件物品注册，服务端与客户端一致） | 0.5 天（与钓竿系统第 1 步共用） |
| 运行时分层物品渲染器（含缓存） | 1~2 天 |
| 装配台自定义 Menu + Screen + 美术 | 1~2 天 |
| Polymer → 真物品迁移（现有物品逐个过） | 1~2 天 |
| 资源包下线 + 素材整理 | 0.5 天 |
| 服务端握手（强制安装校验） | 0.5 天 |
| 每轮客户端实机回归 | 0.5 天/轮 |
| **合计** | **约 5~8 个工作日（≈ 8~12 轮提交）** |

## 5. 与钓竿系统的衔接（顺序）

1. **数据契约**：定下钓竿的组件结构（部件 / 升级 / 耐久 ×10）并实现最小版本（只做注册与读写，不做玩法）；
2. **客户端渲染**：分层渲染器读该组件 → 杆 / 线 / 钩 / 升级逐层画；
3. **客户端界面**：装配台自定义菜单与界面（不再受"借壳换皮"限制，也没有副作用）；
4. **服务端玩法**：属性公式、材料消耗、修补/换底、铁砧升级、断线、青金石附魔（全部按[钓竿系统方案](钓竿系统方案.md)）；
5. **清理**：删掉借壳菜单与换皮方案、去掉 Polymer 依赖、关掉资源包下发；
6. **收尾**：握手校验（强制安装）+ 文档与安装说明更新。

> 注意：第 2、3 步虽然"先做"，但依赖第 1 步的组件契约 —— 不能真的"零服务端"起步。

## 6. 决策回顾（为什么不能既要又要）

- 运行时逐层渲染 + 自定义界面 → 必须有客户端模组；
- 客户端模组一旦"强制"，原版客户端就不再是目标 → **资源包与 Polymer 映射也就失去意义**，可以下线；
- 反之若哪天想回到"原版客户端也能玩"，就必须保留 Polymer + 资源包 + 借壳界面那一整套 fallback（成本翻倍）。**当前选型是彻底放弃原版客户端兼容**。

## 7. 未决项

1. **分发渠道**：自己服的群文件/PCL 整合包，还是也发 Modrinth？（严格同版本下需要一个可靠的更新入口）
2. **过渡期**：先让"装了客户端才有新外观、没装仍能玩"过一版（更平滑），还是直接切强制？
3. **握手实现**：登录后握手失败时是"直接踢出（带提示与下载地址）"还是"允许进服但屏蔽相关功能"？
