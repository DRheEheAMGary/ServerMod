# 分发与更新

> 状态：渠道已定，自动更新按需推进。
> 配套：[客户端契约](客户端契约.md)（改什么要发客户端）、[客户端模组方案](客户端模组方案.md)、[路线图](路线图.md)。

## 1. 渠道（已定）

- **产物**：GitHub Release，一次两份 —— 服务端 jar + 客户端 jar；
- **版本源**：GitHub API，或自己维护的一个静态 JSON（更稳，可放多个源）；
- **下载镜像**：群文件 / 网盘直链（国内网络下这才是玩家真正下得动的）；
- **不上 Modrinth / CurseForge**：平台规则对 AI 生成内容、运行时下载代码都有约束；而且这是私有服务器专用模组，上架没有收益。

## 2. 两个独立版本号

| | 规则 |
|---|---|
| `server_version` | 每个 release 递增 |
| `client_version` | **只在客户端真的改了才递增**；没改就一直是 `1.0.0` |

- **每个 release 都挂上"当前应使用的客户端 jar"**：没改就挂同一份（文件名带 `client_version`，内容不变）。
  这样"该下哪个"永远只有一个答案 = **最新 release**，新玩家不用翻历史；
- 根 `gradle.properties` 拆成两个字段（不能再是一个共享的 `mod_version`）。

## 3. Release 说明模板

> 命名约定：**tag 与 Release 标题都带 `v`** —— tag `v0.5.0-beta.1`、标题 `HubSuite v0.5.0-beta.1（一句话）`。
> jar 文件名里的版本号**不带 v**（`hubsuite-0.5.0-beta.1.jar`），因为那是版本号本身。

顶部醒目区块，三档选一：

`~markdown
## 客户端
✅ 无需更新 —— 继续用 v1.0.0 客户端
⬆️ 建议更新 —— 客户端 v1.1.0（有新表现，不换也能玩）
⚠️ 必须更新 —— 客户端 v1.1.0（进服要求 ≥ v1.1.0）

## 服务端
v1.3.0
- …

## 最低客户端版本
MIN_CLIENT = 1.0.0
`~

- release **标题**也带标记：`HubSuite 1.3.0` vs `HubSuite 1.3.0（含客户端更新）`；
- "必须更新"那一档 = `MIN_CLIENT` 被抬了，**代码与说明必须同时改**，不能只改一处。

## 4. "客户端要不要改"怎么判定

按[客户端契约](客户端契约.md) 第 2 节的分级表。可选省心机制：构建时对比本次与上一版客户端 jar 的**指纹**，release 脚本自动打印"客户端有/无变动"，照着填说明，不靠记忆。

## 5. 自动更新（三档，按需上）

| 档 | 做法 | 玩家操作 | 现在做吗 |
|---|---|---|---|
| ① 检查 + 提示 | 启动时查版本源，有新版就提示 + 一键打开下载页 / 复制链接（约 50 行） | 手动下载替换 | **做**（成本极低，也是其它档的兜底） |
| ③ 启动器托管 | HMCL「服务器自动更新整合包」（自托管，不碰平台），顺带能管 Fabric Loader 与 MC 版本 | 零操作 | 玩家以 HMCL 为主时做 |
| ② mod 自更新 | 下载新版 → 退出后由 JVM **之外**的一步替换 `mods/` 里的 jar | 只需重开游戏 | 暂不做 |

**为什么 ② 需要"JVM 之外的一步"**：运行中的 jar 在 Windows 上被 JVM 占用，删不掉也改不了名；而 Fabric 在加载阶段就解析 mod，新旧两个版本同时在 `mods/` 里会重复 mod id 直接崩。所以替换只能发生在游戏退出之后（脚本或 helper 进程）。代价：杀软误报 + 下载成功率。

**硬约束**：跨 MC / Fabric Loader 版本升级，自动更新救不了（新客户端要新 Loader），必然要人工换一次。

## 6. 国内网络

- 版本检查走**小 JSON**（几十字节），可放多个源，超时 3 秒；
- 实际 jar 下载走**镜像**（群文件 / 网盘 / Gitee release）；
- 检查失败**必须静默降级**：不卡启动、不弹错误框，当作"没有新版本"处理。

## 7. 公告位（三处同步）

抬 `MIN_CLIENT` 时：release 说明顶部 + 服务器描述（MOTD）/ 入服提示 + 群公告。
