# 客户端契约 v1

> 状态：**草案，1.0 冻结**。0.5 的实现依据；1.0 之后对外承诺的兼容基线。
> 配套：[客户端模组方案](客户端模组方案.md)（选型与工作量）、[分发与更新](分发与更新.md)（怎么发到玩家手里）、[路线图](路线图.md)。

## 0. 前提与边界

- 客户端**强制安装**：不装进不来（硬门槛，长期不变）；
- 服务端支持 `MIN_CLIENT` 以上的**所有**客户端：区间内功能降级，**不拒绝**；
- 只保证**同一个 Minecraft 版本内**（26.1.2）。跨 MC 版本必然要换客户端 —— 能承诺的只是"数据契约不变，重编译是机械劳动"；
- "客户端要改"不等于"玩家要手动换"：小版本改动可以靠自动更新消化（见[分发与更新](分发与更新.md)第 5 节）。

## 1. 判定规则（一句话）

> 只有当服务端想表达的东西，客户端**没有任何代码或素材能表达**时，客户端才必须改。

推论：客户端不是"一堆预先做好的物品和界面"，而是**只认描述、不认具体 ID 的解释器**。

## 2. 改动分级表

| 服务端改动 | 客户端 | 原因 / 怎么做 |
|---|---|---|
| 数值 / 配方 / 掉落 / 概率 / 成本 | 不发版 | 纯数据 |
| 新物品（复用已有材质与形状） | 不发版 | 渲染由服务端组件数据驱动 |
| 改界面布局 / 槽位 / 图标 | 不发版 | 槽位由服务端菜单提供 |
| 新 tooltip / 文本 / 提示 | 不发版 | 服务端文本组件 |
| 纯服务端逻辑（不产生新表现） | 不发版 | — |
| 协议新增字段（服务端只多发） | 不发版 | 只增不改 + 容忍未知字段（3.1） |
| 新音效 | 不发版 | 用原版 sound event |
| **新材质（新贴图）** | **小版本** | 加一张图 + 映射表一行（约十分钟） |
| **新方块 / 新界面底图** | **小版本** | 素材而已 |
| 新形状 / 新交互范式 | 大版本 | 需要新的渲染或交互代码 |
| 需要客户端主动上报新数据 | 大版本 | 未预埋通用通道（第 7 节） |
| MC / Fabric Loader 升级 | 大版本 | 无解 |

## 3. 四项廉价预埋（必做）

都是几十行甚至零行的东西；砍了会在旧客户端上直接出问题。

### 3.1 协议只增不改

- **写方**：新字段一律追加在 payload 尾部；旧字段永不改序、改型、删除；
- **读方**：读到多余尾巴直接忽略，不做长度断言；
- 每个 payload 首字段放一个 `u8` 协议号，方便将来分流；
- **黄金字节测试**（没有旧客户端在手上时唯一能自动守住的防线）：
  - 把 1.0 客户端每种 payload 的编码样本存进仓库（十六进制常量或 `src/test/resources/contract/*.hex`）；
  - 服务端自检断言：新读方能解析**全部**旧样本；新写方写出的字节在**旧字段前缀上逐字节一致**；
  - 加字段 → 必须同时加一条新样本，**旧样本不许改**。

### 3.2 未知即占位

- 客户端遇到不认识的材质 id / 形状 / 菜单元素：画统一占位（灰底问号），**不抛异常、不出紫黑格**；
- 日志按 id 去重，只写一次（防刷屏）；
- 服务端遇到客户端报来未知的能力名：忽略，不报错。

### 3.3 能力握手

- C2S（登录后立即）：`{clientVersion, protocol, caps[], fingerprint}`
- S2C：`{ok, serverVersion, minClient, serverProtocol, reason?}`
- 未应答（= 没装客户端）→ 踢出并给下载地址；
- `caps` 命名：小写 + 下划线，如 `rod_render_v1` / `assembly_gui_v1` / `generic_menu_v1`。**只增不减**：废弃的能力保留在列表里，但服务端不再依赖它；
- 服务端按 `caps` 分叉，并在入服日志里记一行（版本 + 指纹 + caps）。

### 3.4 版本与指纹上报

- 客户端版本号**独立于服务端**（客户端 `1.0.0` 可以横跨服务端 `1.0` ~ `1.7`）；
- 指纹 = 构建时对"客户端源码 + 素材"算 hash，写进 jar（`fabric.mod.json` 的 custom 字段）；
- 用途一：出问题时立刻知道玩家在跑哪个客户端；用途二：release 说明自动判定"客户端有没有变动"。

## 4. 降级底线（不可协商）

1. 未知内容 → 占位 + 一次性日志；
2. 旧客户端**绝不**因为服务端新增内容而崩溃或错误刷屏；
3. 服务端**绝不**因为客户端报来未知能力而行为异常（忽略未知，按最低能力走）。

## 5. 版本与门槛

| 项 | 规则 |
|---|---|
| 硬门槛 | 装了客户端 **且** `clientVersion >= MIN_CLIENT` |
| 软区间 | `MIN_CLIENT` ~ 最新 → 放进来，按 caps 降级 |
| 抬 `MIN_CLIENT` | 只在"旧客户端缺了**无法降级**的东西"时抬；抬的时候 release 说明必须同步写"必须更新" |
| Fabric `depends` | 客户端 `fabric.mod.json` **不得**对服务端版本做精确依赖（宽区间或干脆不写）。Fabric 只负责"装没装"，"够不够新"全部由握手判定 |

## 6. 1.0 冻结清单

1.0 发布后以下内容只能追加，不许再动：

1. 频道名（`hubsuite:*`）；
2. 每个 payload 的字段顺序与类型；
3. `caps` 名称与含义；
4. 菜单类型 id 与槽位语义（哪个槽接受什么、点什么触发什么）；
5. 素材路径与命名约定；
6. 占位图 id；
7. 握手指段与 `MIN_CLIENT` 的语义。

## 7. 明确不做（省下的复杂度）

| 不做 | 理由 | 代价 |
|---|---|---|
| 参数化调色 / 材质槽 / 光泽参数 | 内容范围自己控制（杆/线/钩十种以内），为"以后可能加材质"养一套引擎不划算 | 新材质 = 发一次客户端小版本 |
| 服务端下发素材（贴图推送 + 客户端动态注册） | 同上；实现与资源重载的坑都不小 | 同上 |
| 通用 KV 上报通道 | 当前没有要收集的客户端状态 | 真要收集时 = 一次客户端更新 |

代价可接受：加一张贴图 + 映射表一行，十分钟，release 说明写一句。

## 8. 待定

- **通用容器界面**：服务端给槽位布局、客户端通用渲染，新台子 = 服务端数据 + 一张底图。
  建议**做**（有多个台子的可能性不低，而每个台子单独写 Screen 的总成本更高），一次性投入约 1 天；
- 若不做：每个新界面 = 一次客户端小版本（也能接受）。

## 9. 验收标准

- **0.6 钓竿系统落地时**：理想 = 客户端版本号纹丝不动；可接受 = 一次小版本（只加贴图）；
- 若需要**大版本**（改协议或渲染架构）→ 说明 0.5 的接口漏了东西，趁早补（1.0 之后补会贵得多）。
